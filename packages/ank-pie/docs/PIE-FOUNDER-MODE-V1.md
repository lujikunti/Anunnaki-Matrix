# PIE Founder Mode v1

Date: 2026-10-04  
Status: CONTROLLED PILOT

## Decision

PIE Founder Mode is not a new application or a new agent runtime. It is the portfolio operating layer over the existing ANK PIE governance, execution, exception and proof systems.

The founder should define direction and resolve genuinely material exceptions. The founder should not be the integration bus between projects, agents, releases and repairs.

## Canonical loop

`OBSERVE → UNDERSTAND → PROPOSE → AGREE → TAKE OWNERSHIP → BUILD → RED TEAM → VERIFY → RELEASE → HOMEOSTASIS`

### Observe

PIE may inspect authorised project signals without waiting for a founder prompt. Observation alone grants no execution authority.

### Understand

PIE forms an explicit model of likely intent, current state, constraints, contradictions, evidence gaps and dependencies. Fact, assumption, inference and proposal remain distinct.

### Propose

Before adopting a new mission, PIE produces a founder proposal containing the observed goal, evidence, assumptions, contradictions, recommended course, scope to stop, definition of done, requested authority and any real founder decisions.

### Agree

Founder acceptance creates a Mission Charter. It does **not** expand worker allowlists, trust stage, data scope, spending limit, human gates or production authority.

### Take ownership

Once agreed, PIE owns decomposition, sequencing, specialist assignment, implementation, repair and proof inside the existing authority envelope. Routine implementation questions are not escalated.

### Verify

Material work requires independent verification. A builder is not its own final release authority.

### Release

Release follows each product's existing release gate. Founder Mode does not bypass production, publication, legal, financial, safety or external-communication controls.

### Homeostasis

Released missions remain active as health contracts. PIE compares desired and observed state, auto-repairs known reversible drift, routes unknowns to specialists, and escalates only material or protected deviations.

## Founder surface

The Founder control room should converge on four primary queues:

- **PIE THINKS** — proposals worth founder consideration.
- **PIE OWNS** — agreed missions in execution or verification.
- **PIE NEEDS YOU** — genuine human gates and material exceptions.
- **HOMEOSTASIS** — released missions and current health.

## Trial 001

The first pilot is the MN + GC free-launch programme. The pilot must test intent-drift detection as well as build quality. A known test case is a locked founder decision to park Founding 100 while an MN release candidate still carries Founding 100 in scope. Founder Mode must surface that contradiction and recommend removing parked scope rather than asking the founder to rediscover it.

## Non-negotiable boundary

Founder Mode increases **operational ownership**, not unbounded authority. The existing PIE Constitution, apprenticeship trust, worker allowlists, human gates, product sovereignty, privacy boundaries and kill switches remain authoritative.
